# 具体实例

> 本页是[第 2 次阶段性评审报告](第2次阶段性评审报告)中测试用例的**逐条实测明细**，
> 共 **132 项**实例，覆盖鉴权、商品、分类、买家意向与口令码、交易闭环与库存、客户账号、
> 搜索浏览、交易历史 8 个模块；结果为 2026-11-05 对当前代码（`v0.2.0` + 第三周增量）
> 在本地 `H2` 环境重启后端后逐条调用所得，**132 项通过、0 项失败**。

## 一、测试环境与数据准备

| 项目 | 内容 |
| --- | --- |
| 后端 | Spring Boot 3 + Spring Data JPA，`mvn spring-boot:run`，端口 `:8080` |
| 数据库 | H2 内存库 `jdbc:h2:mem:mall`，`ddl-auto=create`，**每次重启自动重建**（保证实例可复现） |
| 初始数据 | 卖家 `admin / admin123`；客户 `buyer1 / 123456`；商品 3 件（在售 2 件、库存 5 / 2，下架 1 件）；两级分类 3 组 |
| 本次新建数据 | 商品：`海盐焦糖手工皂`（stock 3→编辑为 4）、`杉木收纳盒`（stock 0）、`亚麻围巾`（stock 2，用于冻结/下架）、`手作陶杯·灰釉`（stock 1，用于单库存与重新排队）、`库存回滚测试品`（stock 1）、`手动下架测试品`（stock 2）；客户：`buyer2 / 123456`；分类：`图书`（一级）→ `文学`（二级） |
| 鉴权方式 | 卖家接口携带请求头 `X-Token`（登录换取）；客户接口同样使用 `X-Token`，两者 token 互不影响 |
| 调用方式 | 本地脚本按“先鉴权 → 再商品/分类 → 再意向与交易 → 最后客户与查询”的顺序串行调用，逐条记录 `HTTP 状态码`、`code`、`message` 与关键字段 |

> 说明：实例编号 `S2-xxx` 便于与第 2 次评审的 TC 编号对照；`对应用例` 列为该实例归属的原始用例编号（TC-A1 / TC-A2 为挑战升级用例）。
> 路径与参数中的 `{商品ID}` / `{意向ID}` / `{口令码}` 为本次运行的实际值占位（H2 重启后 ID 与口令码会重新生成）。

## 四、实测中确认的边界行为

除正例与反例断言外，以下 4 条边界行为在实例中被显式验证，容易与“直觉预期”相反：

1. **提交意向即预占库存**：`S2-073` 中 3 条意向提交后，商品库存由 4 直接降到 1；库存归零的商品状态转为 `OFF_SHELF` 且 `autoOffShelf=true`（`S2-013`）。因此“已下架仍能提交”的现象多是**预占后自动下架**造成的先后顺序差异，而非校验失效。
2. **自动下架 ≠ 手动下架**：库存归零自动下架的商品仍可进入交易（`S2-098`），已被排队的意向口令码也仍然可用；只有卖家**手动下架**才会让口令码失效（`S2-110`）。
3. **成交后库存可能回到在售**：多库存商品成交后，若仍有库存，商品回到 `ON_SALE` 继续销售，而未成交的等候意向全部转为 `VOID` 并释放预占库存（`S2-090`、`S2-091`）。
4. **分类编辑必须带名称**：`PUT /api/seller/categories/{id}` 的请求体 `name` 为必填（`@NotBlank`），只改排序也需要回传原名称（`S2-046`），这是当前实现的约束，前端已按此传参。

## 五、复现方式

```bash
# 1. 启动后端（H2 内存库，每次启动都是全新的种子数据）
cd backend && mvn spring-boot:run

# 2. 确认服务就绪
curl http://localhost:8080/api/products

# 3. 按本页顺序执行实例（示例：未登录访问卖家接口应返回 401）
curl -i http://localhost:8080/api/seller/products
```

> 实例之间的数据存在先后依赖（例如先建商品再有意向），建议按编号顺序执行；若中途状态被改动，重启后端即可回到初始数据。
